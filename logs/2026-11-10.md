## gitpush に pull（rebase）対応（issue #22）

- **実発生**: Actions が途中で push して remote が進むと、`gitpush.mjs`（add → commit → push のみ）が
  non-fast-forward で失敗 → 未pushコミットが残る → 別ターミナルで `git pull` →
  「divergent branches」fatal（`pull.rebase` 未設定）→ 設定変更 → merge → 手動 push、という手順が必要になった。
  **配合が成功するたびに remote が進むため再発しうる**。
- **修正（`scripts/gitpush.mjs`）**: `add → commit → fetch → 必要なときだけ pull --rebase → push`。
  - `--rebase` は**明示フラグ**なので `pull.rebase` 設定に依存しない（command-line が設定より優先）。
  - rebase は remote のコミットを土台に載せるため **merge commit を増やさない**。
  - `fetch` は非破壊、**behind 0 なら pull を呼ばない**（通常は従来どおり速い）。
  - **「変更なし」判定を修正**: commit すべき変更が無くても **未pushコミット（ahead > 0）があれば push**。
    （「変更がないため push は行いません」と出たのに押されていない状態を解消）
  - rebase コンフリクトは手動手順を表示して **exit 1**（自動解決しない）。
- **検証中に発見した危険挙動（初版）**: コンフリクトで rebase が止まった**次回実行**で `add -A` が
  **コンフリクトマーカー付きの状態を丸ごとコミット**しかねない（実再現）。あわせて rebase 中は
  `rev-parse --abbrev-ref HEAD` が `origin/HEAD` 系を返す。
  → **`rebase-merge` / `rebase-apply` / `MERGE_HEAD` / `CHERRY_PICK_HEAD` を開始時に検知して
  `add -A` の前に停止**、ブランチ名が `HEAD` / `origin/HEAD` 系なら停止。
- **検証（一時リポジトリ・ローカル bare remote で SSH不要）**: 全7分岐を実行 —

## 配合申請の重複判定と生成結果キャッシュ（issue #37）

- **依頼**: 同じ配合条件で何度申請しても生成AIを再実行しない。ただし配合タイプやコメントが違えば、
  同じ親の組でも新しい発明を生成できるようにする。キャッシュヒットは**失敗ではなく正常な処理**として扱う。
- **重複判定の条件（4項目すべて一致で「同じ配合」）**: 親A / 親B / 配合タイプ / コメント。
  - 親の順序は区別（`A × B` と `B × A` は別物）。
  - コメントは改行コードを `\n` に統一し前後の空白を除去。**空白だけのコメントは「なし」と同一**。
    内容が違えば別配合。
  - キーは `SHA-256(canonicalJSON({parentA, parentB, mode, comment}))`（小文字16進64文字）。
    **Issue番号・申請日時・スロットは含めない**（`BreedingRequest.slot` を意図的に除外）。
- **変更ファイル**:
  - `lib/breed-key.ts`（新規）: `normalizeComment` / `canonicalCondition` / `requestHashOf` / `isRequestHash`。
    `node:crypto` だけを使う Node 専用モジュール。**`lib/index.ts` からは再エクスポートしない**
    （フロントのバンドルに node コードを混ぜない）。
  - `lib/queue.ts`: 親ペアだけの重複却下（`samePair` + `offspringPairs`）を廃止し、
    `existingByRequestHash: Map<hash, offspringId>` による照合へ変更。一致したら **`action: 'reuse'`**
    （`existingId` 付き）を返す = 却下ではない。**祖先×子孫の却下は維持**（条件が一致しても先に却下）。
  - `lib/types.ts`: `Offspring.requestHash?: string` を追加（既存データは無くてもよい）。
  - `lib/github.ts`: `getIssue(number, opts)`（state不問で1件取得）。元Issue本文の復元に使う。
  - `scripts/process-breeding.ts`:
    - 選択前に**配合条件インデックス**を構築。`requestHash` 無しの既存データは元の申請Issue本文を
      `parseBreedingIssue` でパースし、**親の並び・配合タイプが保存データと一致するときだけ**ハッシュ化して登録。
      取得失敗・不一致・参照なしは**推測せず**「重複判定できない既存データ」としてログに明示（対象外）。
    - `reuse` 分岐（却下処理より前・間隔ゲートより前）: AI 0回 / ID採番なし / 画像なし / **既存の発明データは変更しない** /
      `tmp/breed-report.md` に既存発明のリンクと「すでに同じ配合で生まれた発明があります」を書いて
      `outcome=reused`（間隔枠も消費しない）。dry-run ではログだけ（書き込み・Issue操作なし）。
    - 通常生成時の保存で `requestHash` を付与し、**そのタイミングだけ**復元ハッシュを既存レコードへ書き戻す
      （§3「キャッシュヒットで既存データを変更しない」と §5「復元してインデックス構築」を両立）。
  - `scripts/validate-data.ts`: 「同じ親の組の重複」チェックを廃止（コメント差異をレコードから判断できないため推測しない）に
    変更し、**`requestHash` の形式（64文字hex）と一意性**を検証。出力に配合条件ハッシュ件数を追加。
  - `.github/workflows/breed.yml`: コメント＆クローズの条件に `outcome == 'reused'` を追加（**再利用でも正常にIssue完了**）。
    Pages再ビルドは `changed && outcome == 'success'` に限定（reused のコミットは processed-issues のみ = 公開内容は不変）。
  - `tests/breed-key.test.ts`（新規8件）/ `tests/queue.test.ts`（重複却下のテストを reuse/新規生成の5件へ差し替え）/ `README.md`。
- **同時実行**: `concurrency.group: breed`（`cancel-in-progress: false`）の直列実行を維持。
  各実行は checkout で最新の `data/offspring.json` を読んでから判定するため、**最新データでの重複判定**になる。
  生成成功 → コメント失敗のような途中失敗でも、次回実行は同じハッシュに当たり **再生成せず reuse で完遂**できる。
- **検証**:
